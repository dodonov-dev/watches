# Liquid Watch: independent development-kit and display survey

Research date: **2026-11-06**. Live vendor/distributor pages and original manufacturer documentation were consulted. Prices are displayed unit prices, generally excluding shipping, import charges and tax; they are not quotations. Stock is a page observation, not a reserved unit. In particular, Shopify pages sometimes expose both “Sold out” and “Add to cart”; those are marked **variant stock unconfirmed**, not in stock.

Scope: web research and reading the five requested project documents only. No code, build, firmware, board or other survey was inspected or changed. All performance figures below are **engineering estimates**, except the explicitly identified project measurements. “Unknown” means the checked sources did not establish the fact.

## Decision

**Stay with the ESP32-P4 ecosystem for the next performance prototype, but select the display and silicon revision deliberately.** There is no verified, immediately orderable, sub-$100, long-bar kit here that also establishes all of BLE, six-axis IMU, RTC, charging and a substantial renderer speed improvement.

The most interesting display-specific lead is **Tailor Pixels TBX175EMD-01 + TOH323XVT-01C**, a vendor-supported P4 evaluation-board combination with a **3.23-inch, 262×928 AMOLED bar**. It has the right shape, black level and pixel count. It is a **quote/sample lead**, not a confirmed retail purchase: RAM configuration, silicon revision, source SDK, complete kit price and delivery need confirmation.

The strongest substantially integrated alternative is **LILYGO T-Display P4 AMOLED**. Its advertised price is above the preferred budget and its 4.1-inch screen/large body overshoot the wearable envelope. It nevertheless combines the relevant faster processor, long AMOLED, IMU, RTC, charger and radio companion. Native resolution is much heavier than the current workload; initially retain approximately the current rendered pixel area.

If the goal is to prove a processor improvement cheaply before selecting a finished cuff, **Waveshare P4-NANO plus a separately sourced bar panel** is the most flexible route. This is an integration project, not an assembled bar-display kit. For a later custom watch, **NXP RT700** deserves more attention than a generic high-clock single-core MCU because its internal SRAM can remove the central memory problem outright. **STM32N6** is the stronger straightforward CPU/SRAM bench alternative, with a larger port and power/size costs.

## What the existing project evidence changes

Read first: [LCD three-tube performance](lcd316-3tube-perf.md), [hardware handoff](hardware-handoff.md), [parts sourcing](parts-sourcing.md), [H573 benchmark plan](h573-bench-plan.md), and [STATUS](../STATUS.md). The separate `docs/devkit-survey.md` was not opened.

* The relevant baseline is the **latest moving three-tube scene: 27.6 fps**, or **36.23 ms/frame**, at stable 80 MHz PSRAM. The 40.7 fps still scene is not the acceptance case. The 31.8 fps moving result at 120 MHz is not a reliable hardware solution because resets wedged.
* The final motion push costs about 9.1 ms summed across strips, with rendering/push overlapped across cores. It is wrong to simply subtract all of that from wall time. Hash-based dirty tracking helps the still scene much more than moving liquid.
* The renderer is already parallel. A single M33 at 160–250 MHz loses that parallelism; “more SRAM” or a GUI accelerator alone does not establish a speed win.
* The H573 document is a **planned renderer benchmark**, not a measured H573 result. Its approximately 375 KB, two-tube memory estimate predates today's full native three-tube/dirty-record configuration. Do not use it as the current complete working-set budget.
* The cuff uses real clear acrylic optics over narrow illuminated slots. AMOLED black is a material advantage over backlit IPS margins, independently of fps. The older 57.5×24.5 mm AMOLED board geometry remains a useful wearable reference, not a constraint already satisfied by a 4-inch dev kit.

All ports must preserve deterministic allocation: reserve buffers, lookup tables, DMA descriptors, GPU command/scratch arenas and radio resources statically or once at boot, sized for the worst supported scene; report failure visibly. No lazy GPU/font caches or heap fallback should be accepted as a memory solution.

## How to interpret speed, bandwidth and frame memory

### Comparable workload and memory arithmetic

Calculated values, using RGB565 at two bytes/pixel:

| Display | Pixels | One framebuffer | Active-pixel reads at 60 Hz, before blanking/other traffic | Pixel count/current LCD |
|---|---:|---:|---:|---:|
| Current 820×320 | 262,400 | 524,800 B = 512.5 KiB | 31.49 MB/s | 1.00× |
| Existing 536×240 AMOLED | 128,640 | 257,280 B = 251.3 KiB | 15.44 MB/s if host-scanned; command GRAM avoids this recurring host read | 0.49× |
| 928×262 AMOLED bar | 243,136 | 486,272 B = 474.9 KiB | 29.18 MB/s if video mode | 0.93× |
| 960×288 IPS bar | 276,480 | 552,960 B = 540 KiB | 33.18 MB/s | 1.05× |
| 1232×568 LILYGO AMOLED | 699,776 | 1,399,552 B = 1.335 MiB | 83.97 MB/s if video mode | 2.67× |

These are full-frame transport/storage figures, not the count of shaded tube pixels. Real workload also depends on physical tube widths, rendered rows, residue and bubbles. Three approximate full-width strips at heights 122+98+73 require **480,520 B** at width 820, or **961,040 B** double-buffered, before row data, hashes, sprites, physics, stacks or framebuffer. Thus a 768 KB headline does not imply that the current whole renderer fits internally. Conversely, fixed small tiles and hot state can benefit greatly without placing every strip internally.

PPI below is calculated as `sqrt(width²+height²)/advertised_diagonal`, rounded. For a **round** display, diagonal is actually the circle's diameter: use **width/diameter**, not the square formula. Mechanical active-area dimensions are preferable for final optics. Marketing diagonals can be inconsistent: the current nominal 3.16-inch 320×820 computes to 279 ppi, while a same-resolution supplier panel with 82.5 µm pitch is about 308 ppi and a smaller active diagonal. Do not finalize a cuff from marketing inches. The [HXD panel specification](https://www.hxd-lcd.com/en/products/detail/2a68506f-6cfc-46a2-814a-9f6ec7c17eef) illustrates this discrepancy.

### Two important P4 corrections as of this date

1. **Revision matters.** Espressif's May 2026 change notice specifies older **v1.3 at 360 MHz CPU / 200 MHz PSRAM**, and **v3.2 at 400 / 250 MHz**. It describes an improved contiguous memory layout, a changed power pin, and different compatible binaries/SDK requirements. It calls for ESP-IDF **5.5.3+ or 6.0+** for the new revision. Ask for the actual silicon marking/revision on an order; a generic “P4 400 MHz” listing is insufficient. [Espressif PCN202600801, especially sections 3–6](https://documentation.espressif.com/PCN202600801_ESP32-P4_Chip_Revision_v3.2_Upgrade_Chip_Revision_v1.3_Demand_Collection_and_EOL_Plan_Description.pdf)
2. **768 KB is a shared L2 memory pool, not 768 KB of application SRAM plus a free large cache.** Cache consumes part of it; ROM/system reservations also matter. Keep the external working set in the bandwidth comparison and budget the actual selected cache configuration. [Espressif ESP-AMP memory explanation](https://github.com/espressif/esp-amp)

The P4 datasheet specifies 16-bit DDR in-package PSRAM; ideal data payload in **x16/HPI mode** is **800 MB/s at 200 MHz**, **1,000 MB/s at 250 MHz**. In **x8/OPI mode**, those figures halve. The S3's octal DDR at 80 MHz is **160 MB/s** ideal. The x16 figures are **5×/6.25× wire ceilings, not measured CPU throughput or fps multipliers**, and do not establish a board's shipped mode. Commands, locality, cache misses, CPU stores and DMA contention reduce usable throughput. P4 also has RGB/I80-class LCD output, MIPI-DSI, PPA and 2D DMA; a raw RGB panel still needs pin breakout and electrical/timing integration. [Current P4 datasheet, memory and LCD_CAM sections](https://www.espressif.com/sites/default/files/documentation/esp32-p4_datasheet_en.pdf), [ESP-IDF external RAM guide](https://docs.espressif.com/projects/esp-idf/en/stable/esp32p4/api-guides/external-ram.html)

### A display accelerator is not a programmable liquid shader

PPA accelerates rotation, scaling, fills and blends. It could replace portions of the quarter-turn/push and suitable compositing passes, but cannot execute arbitrary refraction LUT gathers, float physics, residue logic or all existing RGB565 blending semantics. DMA2D, PXP and fixed-function 2D GPUs have the same basic qualification. Savings require restructuring selected passes, extra memory traffic and cache synchronization; bit-exact output must be checked. **Do not multiply the entire renderer by a vendor LVGL benchmark.** [Espressif PPA API](https://docs.espressif.com/projects/esp-idf/en/stable/esp32p4/api-reference/peripherals/ppa.html)

**GRAM classification:** RGB or DSI **video** mode requires a recurring host stream. QSPI/8080 or DSI **command** mode with usable full-frame panel RAM can retain the picture and accept dirty rectangles. DSI alone does not prove either behavior. A panel may contain RAM yet still be configured by its BSP for video streaming. For unverified modes, estimates conservatively retain host scan-out.

## Ranked candidate details

### 1. Tailor Pixels P4 AMOLED bar evaluation combination

**Vendor evidence.** [TBX175EMD-01 board](https://tailorpixels.com/product/esp32-display-board-eval-kit-for-am-oled-displays/) is listed at **$20–40**, with 48×48 mm board dimensions, USB-C 5 V, microSD, touch and MIPI. The [vendor's evaluation compatibility page](https://tailorpixels.com/esp32-amoled-display-board-amoled-eval-kit/) explicitly lists the **TOH323XVT-01C bar**, plus 410×502, 368×448 and other AMOLEDs. It offers firmware support/sample quotations, not a checkout-confirmed assembled kit. Neither page establishes the board's flash/PSRAM size, radio, IMU, RTC or LiPo charging. Treat those as **unknown/unprovided**, not inherited from another P4 board.

**Display.** [TOH323XVT-01C](https://tailorpixels.com/product/3-23-inch-bar-amoled-with-on-cell-touch-262x928-mipi/): **$26–33**, 3.23-inch AMOLED, **262×928**, approximately **299 ppi**, aspect **3.54:1**, on-cell capacitive touch, RM690C0 display driver/ ZT2628 touch. The [June 2026 module specification](https://tailorpixels.com/wp-content/uploads/2026/06/TOH323XVT-01C_3.23-inch-Bar-AMOLED-with-On-Cell-Touch-262%C3%97928-MIPI-20260609.pdf) specifies **one-lane MIPI**, 22.008×77.952 mm active area, **500 nit typical**, and 0.83 mm module thickness. The page also mentions QSPI, 700 nits and 0.63 mm elsewhere; use the module PDF rather than assuming those conflicting claims apply to the delivered SKU. Source timing and full-rate refresh remain unconfirmed.

**GRAM:** the [Raydium RM690C0 controller sheet, publicly served by display supplier DWO](https://18746902.s21i.faimallusr.com/61/1/ABUIABA9GAAglJqgswYokKaOjwc.pdf) establishes display RAM and command/video operation at controller level. Its listed resolution options do not directly establish this unusual 262×928 module mapping. **Full-frame retained command-mode operation on this bar/BSP is therefore unverified.** The [P4 board specification](https://tailorpixels.com/wp-content/uploads/2026/06/TBX175EMD-01-ESP32P4-Display-Board-Eval-Kit-for-AMOLED.pdf) describes MIPI DPI pixel-clock/porch settings for its examples: assume recurring host streaming until the vendor supplies an exact command-mode example.

**Processor/SDK:** P4 architecture and PPA as discussed above; board clock/revision and external RAM population unknown. ESP-IDF is the natural renderer target, but a downloadable source BSP for this exact combination was not established. **Port: low–medium if source drivers are supplied; high risk if only factory binaries are supplied.** Adding C6/BLE, IMU, time backup and charging may require a carrier.

**Estimate:** with a normal 32 MB P4 memory configuration, around **1.5–2.5×** the current moving-scene throughput at comparable shaded pixel count, roughly **40–70 fps render throughput**; actual visible fps cannot exceed the confirmed panel refresh. No extra GRAM benefit is assumed. This is the most geometrically attractive lead, but its unspecified memory prevents a firm performance prediction. The simple **$46–73 sum is only two listed price ranges**; it does not prove sample quantity pricing, inclusion of adapter, stock, freight or a sub-$100 delivered kit.

### 2. LILYGO T-Display P4 AMOLED / TFT

[Vendor product](https://lilygo.cc/products/t-display-p4): **$119.30 displayed**, AMOLED 4.1-inch and TFT 4.05-inch variants; **63×109×22 mm** product. Both “Sold out” and purchase controls appear; variant/warehouse availability is **unconfirmed**. [Official wiki](https://wiki.lilygo.cc/products/t-display-series/t-display-p4/) documents **ICM20948 nine-axis IMU**, PCF8563 RTC, LGS4056H charger, BQ27220 gauge and ESP32-C6 radio companion. The C6 provides BLE/Wi-Fi hardware; the exact shipped companion firmware must be considered separately from the radio specification.

| Item | Verified/configuration qualification |
|---|---|
| Main processor | Dual RISC-V P4 advertised at **360 MHz**, LP core 40 MHz; do not silently upgrade this particular listing to 400 MHz |
| Memory | 768 KB family L2 pool, subject to cache/reservations; **32 MB in-package PSRAM**, **16 MB main flash**; actual OPI/HPI mode/clock not established by board page, 200 MHz is the conservative older-revision reference |
| AMOLED | **4.1-inch 568×1232**, approximately **331 ppi**, aspect **2.17:1**, RM69A10, MIPI-DSI |
| TFT alternative | **4.05-inch 540×1168**, approximately **318 ppi**, aspect 2.16:1, MIPI; exact IPS designation not established in checked product text |
| Host versus panel memory | AMOLED full GRAM/command-mode use **unknown**; conservatively budget a host framebuffer/stream. TFT also needs a host framebuffer unless explicitly demonstrated otherwise |
| Acceleration | PPA, 2D DMA; no general programmable GPU shader |
| SDK and port | ESP-IDF primary, PlatformIO/vendor examples; **low–medium** for scalar renderer/drivers, **medium** for radio companion and accelerator integration |

The [manufacturer source repository](https://github.com/Xinyuan-LilyGO/T-Display-P4) distinguishes V1.0 from **V2.0 evaluation-preview** documentation. A preview schematic is not proof that retail stock is the new revision. Its reset/power behavior and peripheral initialization also deserve attention when choosing the BSP.

**Estimate:** at today's rendered pixel area, **1.5–2.5×** moving-scene throughput is a reasonable test hypothesis. Native full-area work has **2.67×** as many pixels as 820×320; under a linear shaded-area model that can consume the entire gain, leaving only approximately **16–26 fps**. Actual fixed physical-width tubes could scale differently. Start with a centered 820×320 canvas or equivalent shaded area, not an assertion of 60 fps at 1232×568. AMOLED black and high density are appealing; the complete device is closer to a handheld prototype than the existing cuff board.

### 3. Waveshare ESP32-P4-NANO + 3.18-inch MIPI IPS bar

[P4-NANO vendor listing](https://www.waveshare.com/esp32-p4-nano.htm): **$18.99 starting board price**, bundles up to $86.99, purchase controls present; warehouse quantity not exposed. The [official documentation](https://docs.waveshare.com/ESP32-P4-NANO) specifies dual **360 MHz** P4 plus 40 MHz LP, **768 KB L2 pool**, **32 MB in-package PSRAM**, **16 MB flash**, and **C6 over SDIO** for Wi-Fi 6/Bluetooth. PPA/2D DMA come with P4. RTC battery header exists, but a six-axis IMU and single-cell system LiPo charger are **not established**; an RTC battery connector is not a charger for the watch battery. ESP-IDF examples exist.

[TTH318BVE-01C vendor panel](https://tailorpixels.com/product/3-18-inch-ips-tft-bar-lcd-mipi-288x960/): **$11.30–18.80 listed range**, quotation/sample availability, **3.18-inch IPS 288×960**, approximately **315 ppi**, **3.33:1**, ST7701S MIPI, capacitive touch, 400 nits, 25.5×85.3×4.19 mm module, 23.07×76.9 mm active area. **No usable full-frame GRAM should be budgeted for the video path**; retain the host framebuffer. It is a stronger geometry/density match than the ordinary 4.3-inch P4 HMI screen.

**Pairing status:** no verified plug-compatible NANO cable or ready-made adapter/BSP for this exact module was found. A DSI connector is not a pinout standard; panel rails, backlight supply/current, connector mapping, lane count, reset/init sequence and touch integration must be matched. The board plus panel price arithmetic is **$30.29–37.79 before adapter/sensors/power**, not a complete kit quote. Do not cannibalize the attached board on the basis of this survey.

**Estimate:** roughly **1.4–2.4×**, or **39–66 fps** moving-scene render throughput at the bar's similar pixel count, conditional on adequate PSRAM mode, a functioning display driver and comparable rendering. Continuous scan-out remains, but substantially faster memory and DMA can ease its competition with strips. **Port: medium overall** because hardware/panel integration dominates; core ESP-IDF renderer work is low. P4-MODULE-DEV-KIT is another supported C6+P4 base at a [starting $19.99](https://www.waveshare.com/product/mcu-tools/development-boards/esp32-p4-module-dev-kit.htm), but its supplied screen bundles are 7/10.1-inch, not a hidden bar option.

### 4. NXP MIMXRT700-EVK, with a future bar module

[NXP EVK](https://www.nxp.com/design/design-center/development-boards-and-designs/MIMXRT700-EVK): **$187.23, three in stock** on the checked page; **$227.93, two in stock** at [DigiKey](https://www.digikey.com/en/products/detail/nxp-usa-inc/MIMXRT700-EVK/28263100). Board-only kit: screen is extra. Compute M33 up to **325 MHz**, sense M33 up to **250 MHz**, plus HiFi DSPs; the two CPUs are heterogeneous subsystems, not a drop-in ESP-IDF SMP replacement.

[RT700 silicon specification](https://www.nxp.com/products/i.MX-RT700?tid=vanRT700): **7.5 MB internal SRAM**, 2.5D vector GPU/OpenVG, framebuffer compression, LCDIF + MIPI DSI, three external xSPI interfaces up to 16-bit/250 MHz DDR. Board memory includes external HyperRAM, flash and eMMC; **the EVK page labels HyperRAM “512 MB,” without a sufficiently verified BOM capacity here**. Do not silently convert that into either 512 MB or 64 MB usable memory. The renderer case can be made with internal SRAM alone; external RAM capacity/rate is not needed to justify this rank.

**Display:** no bundled bar. NXP lists an optional **1.43-inch wearable MIPI display at $90** and larger 5.5-inch 720×1280 TFT options; neither matches the long cuff. Integrating the 3.18/3.23-inch panels above is an **unverified new pairing**. Their geometry/GRAM qualifications carry over. Radio requires an expansion/companion module; six-axis IMU and LiPo charging were not established on the checked EVK. The MCU timekeeping facility is not equivalent to a documented complete watch RTC/backup circuit.

**SDK/effort:** MCUXpresso SDK and Zephyr ecosystem, GPU support; **high** for board/radio/display and explicit multicore ownership/cache coherency. A current [NXP custom MIPI-driver integration note](https://docs.nxp.com/bundle/AN15175/page/topics/introduction.html) is linked from the EVK documentation, which is useful evidence that custom panels are an intended workflow, not evidence that this particular bar is already supported.

**Estimate:** **1.2–2.2×** for an initial scalar port with hot work in SRAM and effective use of both CPUs; roughly **33–61 fps** at today's workload. Low confidence: the per-core clocks alone do not beat two 240 MHz S3 cores decisively. The major gain is stable internal storage and independent display access, with additional GPU savings only after targeted changes. Its 7.5 MB is **14.6× the S3's gross 512 KB**, enough in aggregate for current framebuffers/strips and substantial state, subject to partition accessibility and scratch reservations. Most attractive MCU family for a memory-first custom watch, not a cheap complete cuff kit.

### 5. STM32N6570-DK

[ST board](https://www.st.com/en/evaluation-tools/stm32n6570-dk) and [data brief](https://www.st.com/resource/en/data_brief/stm32n6570-dk.pdf): single **Cortex-M55**, [up to **800 MHz**](https://www.st.com/en/microcontrollers-microprocessors/stm32n657x0.html), **4.2 MB internal SRAM**, **32 MB hexadeca-SPI PSRAM**, 128 MB external NOR. **5-inch touch TFT**, 800×480, approximately **187 ppi**, RGB/LTDC display path with a host framebuffer; full panel GRAM not established or required for that path. NeoChrom 2.5D GPU, DMA2D and LTDC; Helium can help selected loops, but requires compiler/algorithm work rather than a free speed multiplier. Confirm actual PSRAM setup in the Cube BSP; x16 bandwidth depends on clock and DDR selection, not just the connector label.

[DigiKey](https://www.digikey.com/en/products/detail/stmicroelectronics/STM32N6570-DK/25724059): **$223.67**, **1,260 in stock** in the retrieved snapshot. No onboard BLE, six-axis IMU or one-cell LiPo charger is listed in the board features. On-chip RTC still needs a suitable backup/power design for a wearable. SDK: **STM32CubeN6**, TouchGFX; **high port effort**, including boot/external-flash setup, memory placement and replacing the current dual-core schedule with a fast serial pipeline.

**Estimate:** **1.8–3.5×**, around **50–97 fps render throughput** at today's shaded pixel count, then limited by panel refresh/transfer. This is a broad hypothesis, not an 800/240 clock ratio: one fast CPU replaces two active CPUs. There is room to reserve approximately 1.0 MB double framebuffer plus 0.96 MB strips and hot state internally in aggregate, with layout/other reservations verified. Useful for software rendering headroom; supplied geometry, bulk and likely system energy make it a bench reference rather than a wearable purchase recommendation.

### Linux-class route: performance is available, wearable fit is the cost

**LILYGO T-Display K230** is the concrete long-AMOLED example rather than a speculative SBC plus unknown screen. ## Panel sourcing findings that affect the choice

* **Exact display class on faster hardware exists as an OEM module, not necessarily a kit.** [YZY 3.16-inch 320×820 ST7701S MIPI module](https://www.yzylcd.com/sale-54979211-3-16-inch-320-820-tft-lcd-module-mipi-interface-st7701s-driver-ic-for-industrial-instrument.html) is listed at **$7.99–10.99 with MOQ 500**; [HXD's equivalent IPS module](https://www.hxd-lcd.com/en/products/detail/2a68506f-6cfc-46a2-814a-9f6ec7c17eef) lists MOQ 100 and quotation. Neither is a verified one-off buy-now P4 assembly. Do not assume the existing board's RGB panel can be changed to MIPI by software; module pinout and bonded interface matter.
* **The “3.9-inch 320×960” search target needs care.** Current catalogs commonly give **3.9-inch 480×128**, **3.99-inch 400×960**, and **4.58/4.6-inch 320×960**. For example, [LCD Mikroelektronik](https://lcd-mikroelektronik.de/en/displays/) lists 3.99-inch 400×960 IPS, 39.18×94.032 mm active area, SPI/RGB, quotation; [Youritech](https://www.youritech.com/products/4-58-inch-stretched-bar-display-rgb-24-bit-320x960-ips-st7701s-bar-lcd-display.html) identifies the larger 320×960 class. No confirmed retail faster-MCU 3.9-inch 320×960 kit was found. Repeating that diagonal/resolution pair without a part number risks buying a much larger screen.
* **Cheap 3.9-inch bars are often a density downgrade.** [BuyDisplay](https://www.buydisplay.com/tft-lcd-display-module/3-9-inch-bar-type-tft-lcd-display-module) lists **$13.28, 480×128, ST7282, RGB**: about **127 ppi**, host streaming. Even a display module with an EVE/SSD1963 graphics controller would not execute this arbitrary per-pixel renderer; it would primarily change the transfer/GRAM architecture.
* **QSPI bar LCD is possible but not automatically high density.** [Tailor Pixels 3.4-inch 180×640 AXS15231 module](https://tailorpixels.com/product/3-4-inch-touch-lcd-in-cell-spi-mipi-qspi-180x64/) lists **$11.50–18.50**, IPS, SPI/QSPI/MIPI, roughly **196 ppi**, quotation. At its low pixel count an S3 may be fast enough; it fails the density preference. Full GRAM/retained behavior must be tied to the selected interface/BSP.
* **368×448 and 410×502 P4 AMOLED combinations are vendor-listed** on [Tailor Pixels' evaluation page](https://tailorpixels.com/esp32-amoled-display-board-amoled-eval-kit/). They are credible sourceable display shapes if the long tubes are abandoned, not equivalent bar displays. There is no reason to rank them above the explicitly listed 262×928 bar for this cuff.

## Recommendation and remaining purchase gates

1. **Best display lead:** request a quotation for **TBX175EMD-01 + TOH323XVT-01C**, including the exact matched adapter and source display driver. Require the actual P4 part/revision, populated RAM size/type/rate, documented refresh, full-screen command-GRAM capability, 262×928 mapping, touch driver and supported ESP-IDF version. Confirm sample quantity and shipping date. The public documents establish a real candidate, but do not establish these missing facts.
2. **Best integrated prototype if its size/budget are acceptable:** select **T-Display P4 AMOLED**, confirm warehouse/variant stock and actual board revision. Its peripherals make it less of a hardware assembly exercise. Start with the current shaded pixel area so the first measurement tests the processor/memory change. Treat full native rendering as a subsequent performance question.
3. **Best inexpensive processor experiment:** P4-NANO with a separately purchased/verified compatible display; the 3.18-inch IPS module is a good panel lead. Reusing the **display protocol class** of the existing QSPI AMOLED is also technically attractive, but no newly researched plug-and-play P4+536×240 retail assembly was verified. Connector/power work remains explicit; this survey authorizes no board modification.
4. **If all-internal working memory is the design priority:** choose **RT700** over RT595/Apollo4/H573 as the serious custom-MCU investigation. Choose **N6** if a comparatively direct fast single-core software-rendering experiment matters more than wearable integration. RT1170 and newer RA8 parts are credible high-performance alternatives if port effort and power are acceptable.

A later benchmark should use the existing moving-liquid scene, three tubes, identical shaded dimensions and active BLE; report motion p95, render versus transfer, PSRAM traffic/underflows and peak reserved memory. Require **30 fps with headroom**, and call **60 fps a target until observed**. No benchmark, purchase, source-tree change, build or board action was performed for this report.
