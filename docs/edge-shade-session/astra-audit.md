# LCD-3.16 renderer precompute audit — `6df29da`

**The largest credible saving is in rear digits.** On the supplied look, about 9,200 hours-tube sprite-run pixels lie clear of the meniscus at the fixed bench pose. The firmware has already baked their glyph colour, shadow, and transparency, but it still composites them against the same row colours every frame. Reusing those finished RGB565 pixels is worth an estimated **1.1–2.7 ms per frame** on the hours core. The next opportunity is the soft edge and meniscus stroke, at roughly **0.4–0.9 ms** when their inputs repeat. A table indexed only by tilt and fill would produce incorrect pixels.

## What the baseline measures

The design-to-board scale is `(0.083 / 0.0825) × (8 / 6) = 1.3414`. The supplied `tubeHeight=54` therefore draws **72 rows**. Each tube contains `820 × 72 = 59,040` pixels, both tubes contain `118,080`, and each tube goes through 18 four-row tiles. Worst-case storage for this build must cover `ceil(80 × 1.3414) = 108` rows. At 240 MHz, **240,000 cycles = 1 ms**. The 16.1 ms hours render is 3.86 million cycles and the 12.0 ms minutes render is 2.88 million. The cores run concurrently, and the 19.0 ms render wall timer includes staggered work. Adding the two core savings, or adding the 2.2 ms push to the 19.0 ms, would overstate the gain. The ranking is by estimated steady-frame saving on the hours core at the fixed pose. Cycle costs are estimates informed by earlier board profiles. ### 1. Cache the finished interior digit runs

`scaledGlyphs` already produces wet and dry colour/alpha planes. `spriteGlyphRows → SpriteRow::seg → spriteRunInt/Frac` still selects source rows, reads the backing, prepares blend lanes, and writes the result for every covered run. At `10:09:30` with the slug home and rear shift settled to zero, hours draws 13 glyphs in labels 1–11. Using the scaled sheet, baked shadow margin and wet/dry source-row maps, I count **9,172 run pixels** after excluding the entire hours label **10**, which the meniscus can cross. The corresponding minutes count is **10,396**, also excluding its edge label **10**. These are run lengths, including transparent holes inside runs. [Glyph bake](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:1866) · [Vertical layout](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:1984) · [Run compositor](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:2645) · [Meniscus columns](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:2734)

Bake the final run against the row’s canonical backing, `pal.rows[ry]` or `pal.tubeBackRows[ry]`, using the existing compositor. Copy it where the glyph has a pure wet/dry share and the actual backing matches. Keep the current compositor for a partial-share column, residue, a tick beneath the glyph, or a glyph overlap whose backing differs. A simple deterministic upper bound is two panel-coordinate RGB565 planes per tube, `2 × 820 × 108 × 2 = 354,240 B` in PSRAM, **708,480 B for both**. Only glyph spans need to be populated or fetched. Key them on glyph/layout generation, row palette and transmission, and the exact rear shifts. Fill changes select or disqualify runs. They need not rebake distant labels.

Allowing for guarded reads and PSRAM copies, `9,172 × 80–100% eligible × 35–70 net cycles / 240,000 = 1.07–2.68 ms`. A complete two-plane rebuild at roughly 20,000 run samples × 60–100 cycles is **5–8 ms per tube**. Rebuilding both planes on every moving-light frame would lose the saving. This differs materially from the earlier, slower variant B, which computed against an assumed background while drawing and changed pixels over ticks and highlights. The backing check and the retained ramp are essential. The sim can use its existing compositor as the reference without changing the appearance. ### 2. Cache the edge’s blend instructions and reuse its row facts

The SIMD soft-edge loop still evaluates floating coverage, quadratic glow and integer alpha per sample. The concave meniscus loop computes coverage, smoothstep, fill, blick and rim, then reduces them to **one source colour and one alpha** before reading the destination. In addition, `wallX` and `concave` run once for the marks’ row facts and again to draw the same stroke. The destination may change with residue even when all those source quantities repeat. [Soft-edge kernel](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:2364) · [Stroke compositor](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:664) · [First row-facts pass](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:4270) · [Repeated stroke setup](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:4735)

For the level, home-settled hours model, the time edge is near `820 × (10 + 9.5/60) / 12 = 694.15 px`. Soft width rounds to **3 px**, glow to **25 px**, and the level wall lead is about **4.72 px**. Evaluating the clipped row ranges gives about **1,570 positive-alpha time-edge ramp samples** and **322 candidate concave stroke pixels**. The home edge is flattened at the end cap, so doubling these counts would be wrong. Estimated saving on a hit is `(1,570 × 45–90 + 322 × 120–230) / 240,000 = 0.46–0.90 ms` before small lookup overhead. This agrees in scale with the older ramp and band kernel profiles. [Geometry](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:3927) · [Kernel cost notes](/home/andrey/_PROJECTS/watches-perf-audit/KAIZEN.md:627)

Store ramp `T` and concave `(RGB565,T)` in PSRAM, plus each run’s start and length. For this build, **64 ramp slots and 32 stroke slots per side per row** cover the slider maxima including rounding and endpoint slack. Payload is `108 × 2 × (64×2 + 32×4) = 55,296 B/tube`, plus row keys and bounds. Rebuild only changed row/side entries, at the cost of those same sample calculations and cache stores. Use exact edge positions, light, pull, row colours, widths and clipping inputs. Apply entries to the **current** backing in the original blend order. Keep short overlapping beads and backing-dependent convex noses on their existing paths. Reusing the row facts within one frame still helps when motion defeats cross-frame hits. The sim can retain the scalar expressions as the oracle. ### 3. Omit the tube-back fill under the guaranteed opaque body

Every band first writes the back across all 820 columns. Later `hspan` overwrites the solid liquid interior on that same internal tile. At the modelled hours fill, the exact solid-span formulas cover about **49,962 pixels**. `hspan` already stores two RGB565 pixels per word. Avoiding `49,962 / 2 = 24,981` word stores at 2–4 loop cycles each gives **0.21–0.42 ms gross**. Extra span boundaries and protected reads bring the estimate to **0.15–0.4 ms**. Minutes, at about 16% fill, benefits much less. [Packed fill](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:1406) · [Back fill](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:4442) · [Opaque interval](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:4583)

Calculate the two solid endpoints once per row and share them between back and body. Two `int16_t` endpoints for four active rows cost **16 B per lane**. Rebuild costs four endpoint pairs per tile, independent of time or tilt stability. Preserve the old backing at the two nose sample locations and throughout AA, crossed-edge and short-bead intervals. This is exact dead-store removal and requires no sim appearance change. [Pre-body backing reads](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:4559)

### 4. Retain the wet-share and mark plans across frames

`buildWetShare` clears a difference array, adds two events per nonempty row, then divides by `H` at **820 columns per tube per frame**. The inputs to the whole result are just the clipped, upward-rounded edge endpoints. `planTicks` and `planLabels` subsequently redo range and glyph-column walks, even though label layout itself is already cached. [Wet-share construction](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:1162) · [Tick ranges](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:3180) · [Glyph plans](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:3278)

Keep the previous endpoint pairs in **432 B/tube** and a **218 B** table for `(n×256 + H/2)/H` at all possible `n`. Reuse the existing PSRAM share and plan arrays. Rebuild the quotient table on height change, the share on changed endpoints, and each plan on changed shares or its own inputs. Tick plans also need exact tick parallax. Glyph plans need both rear shifts, layout, and glyph generation. Live per-row edge and band facts still govern compositing. Avoiding `820 × 15–35 cycles` gives **0.05–0.12 ms** for the column pass alone. Skipped mark-plan walks bring the settled estimate to **0.1–0.35 ms**. A miss costs the existing `O(H+820)` pass and ordinary plan build. The risk is stale plans after a layout or shift change. The sim already defines the same integer wet share. ### 5. Cache each fizz slot’s vertical projection at its exact floating-point row

`planBubble` computes `fizzMag` using **two interval means**, then derives vertical radius, light direction and offsets. On this vertical watch at zero across-tilt, a freely travelling bubble can advance in `x` while its `y` stays exactly fixed. Its horizontal position and clipping still change. [Projection](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:3828) · [Bubble setup](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:4976) · [Position update](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:3743)

A **32 B entry × 480 slots = 15,360 B/tube** in PSRAM can hold exact `y`/radius keys and projection results, with a per-tube lens/light generation. Recompute on spawn, changed `y`, radius, light or lens. Popping bubbles can use the analytic path. At an illustrative **40–90 qualifying bubbles**, `40–90 × 350–800 net cycles / 240,000 = 0.06–0.30 ms`. Actual live counts for the supplied JSON were not captured. `fizzCount=120` is a full-tube density, and this spring emits at nine per second. A rebuild is one ordinary projection per missed slot. Rounding `y` to a row would change the intervals selected by `floor(y−r/m)` and `ceil(y+r/m)`. An exact slot key preserves sim parity and leaves foam contacts, movement and draw order live. ### 6. Move the fizz depth-colour rebuild to palette invalidation

`planFizz` fills `cRim[level][row]` and `cBlick[level][row]` every frame. The arrays already exist. Their inputs are the palette, brightness, depth and transparency. Bubble positions and fill are absent. This look executes `4 levels × 72 rows × 2 colours = 576` colour calculations per tube. At 25–60 cycles each, that is **0.06–0.14 ms**. [Per-frame loop](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:5146) · [Existing palette invalidation](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:5390)

Use the existing palette rebuild key and parameter generation. **No new payload storage** is needed. A miss costs the same 576 calculations. Keep the following veil-bound loop with the moving surfaces. This is the lowest-risk change in the list and preserves the existing colour rounding.

### 7. Cache residue row constants and settled visibility

Even on a `traceBlur` hit, each active residue row reconstructs `kRow`, `K`, six colour-log terms and a visibility decision. The geometry terms depend on row geometry, the logs on two RGB565 palette entries, and the no-visible-coat proof on the trace maximum and gain. On clear glass with this JSON’s permanent film alone, `eta ≤ 0.1 × 0.0002`, so the rounded column coefficient is at most **3**. Evaluating the existing depth formula at that upper bound leaves only **six of 72 rows** potentially visible. This is why the older multi-millisecond residue figures for heavy film do not transfer to this look. About **32 B × 108 = 3,456 B/tube** in PSRAM holds the row geometry and colour terms. Rebuild on geometry or palette change for `O(H)` work. ## Where the belief stops holding

- **A whole wet/dry image indexed by fill or tilt is insufficient.** The same fill can have different slug position, pinned contact leads, edge velocities, wet history, light, and rear shifts. A partially covered glyph uses the column’s wet share to select its warp while the destination row selects its backing. The earlier layer-cache handoff explicitly accepted a meniscus mismatch. That concession and the rejected half-wet digit shortcut conflict with the current parity requirement. [Layer-cache handoff](/home/andrey/_PROJECTS/watches-perf-audit/docs/perf-handoff-3-layer-cache.md:25) · [Digit variant results](/home/andrey/_PROJECTS/watches-perf-audit/docs/lcd316-perf-plan.md:669)
- **A pristine pre-fizz image can be exact, but a full-image copy has a real break-even point.** One live strip is **118,080 B**. At the repo’s older measured 26–43 MB/s transfer rates, one additional full-strip transfer takes **2.75–4.54 ms per tube** before drawing fizz. Those rates are illustrative for this board build. A bounded implementation needs **177,120 B/tube** at maximum height. Sparse restoration could do better, but it must restore both old and new bubble footprints, replay overlaps in slot order, and preserve pre-lens pixels on this JSON’s strip-lens path. This is why I rank sparse digit reuse ahead of a full backing image. [Transfer measurements](/home/andrey/_PROJECTS/watches-perf-audit/docs/lcd316-perf-plan.md:613) · [Dirty-region handoff](/home/andrey/_PROJECTS/watches-perf-audit/docs/perf-handoff-4-dirty-region.md:12)
- **Much of the proposed parameter precomputation already shipped.** Row warps, cap coordinates, magnification, lens source rows, exact-light palette caching, glyph scaling and shadow planes, residue blur/streak memoization, 12 fizz size classes, four depth levels, and coverage masks are present. Tile hashes already reduce the eligible LCD push *after* rendering. They do not eliminate the original paint. New tilt bins would introduce visible thresholds where the current code uses exact light or already-defined 1/16-pixel shifts. [Row cache](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:3953) · [Fizz classes and masks](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:4875) · [Tile completion and hashing](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:4425)
- **Physics and disabled effects contribute no bankable lookup-table saving here.** Moving foam contacts, pop age, spring births and shifted residue samples depend on current state. The separate `bubble`, `frontBright` and `highlightInset` passes are off. With `edgeSoft > 0`, glow is already part of the AA ramp. Charging another glow pass, the full fizz step, or the assigned shade saving would count work twice. [Effect gates](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:4639) · [Fizz step](/home/andrey/_PROJECTS/watches-perf-audit/firmware/src/render.cpp:3672)

All storage figures assume fixed arrays or a single worst-case boot allocation in the specified memory, with visible allocation failure. The audit was read-only, with no serial access or new device benchmark. The decisive measurement for item 1 is **eligible rear-digit run pixels and net cycles per copied pixel on the hours core**. That would test the largest estimate without conflating it with the shade path or minutes-core slack.
